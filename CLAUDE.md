# CLAUDE.md — betterchange-consulting.de

Context and conventions for any Claude Code session working on this repo. Read this in full before making changes. If you discover a new convention, gotcha, or decision during your session, **add it here** so other sessions (running on other branches) benefit from it too.

## Project overview

Full rebuild of betterchange-consulting.de from Wix Studio to a coded Astro site, deployed on Netlify. Bilingual site (English + German), stack: Astro, Netlify, GitHub, Google Workspace SMTP for email, Lexware Office XL for invoicing (Mollie card payments planned as a later phase, not yet built).

As of the v2.0.0 milestone: the entire site is live in both languages, including all core pages, the training/course/register flow, and all 81 "quality-tier" Insights articles. Two things remain deliberately deferred (not forgotten — see "Deferred work" below).

## Merge policy

Never merge to `main` without asking first. When your work is ready and all pre-merge checks pass, stop and ask Russ for explicit approval before merging — do not merge automatically even if everything looks clean. This applies to every branch, every time.

## Known recurring bugs / gotchas

**Static-site staleness for date-based listing filters.** "Upcoming course" filters (`src/lib/dates.ts`) only re-evaluate `new Date()` at build time, not per-visitor. A `netlify/functions/nightly-rebuild.js` Scheduled Function (schedule declared in `netlify.toml`'s `[functions."nightly-rebuild"]`, since this repo doesn't use the `@netlify/functions` package's inline-schedule helper) triggers a Netlify build once a day so a session that's crossed its listing cutoff actually drops off the live site. **Requires a `NETLIFY_BUILD_HOOK_URL` environment variable** set in Netlify (Site configuration → Environment variables), pointing at a Build Hook created under Site configuration → Build & deploy → Build hooks — this is a manual, one-time setup step in Netlify's dashboard that no session can do itself. Without it, the function fails loudly (visible in its logs) rather than silently doing nothing.

**Netlify stale-build issue.** Deploy logs sometimes show "All files already uploaded by a previous deploy with the same commits" while the live site keeps serving old output. Standard "Trigger deploy" / "Retry" does NOT fix this. Use **"Clear cache and deploy site"** specifically in the Netlify Deploys tab. This has recurred multiple times across this project — if a change isn't showing live after a normal deploy, this is the first thing to try before assuming the code is wrong.

**Locale-aware links.** Every href that could point to a page with both an English and German version MUST be prefix-aware (`${prefix}/...`), not hardcoded. This bug has recurred multiple times: `registrationHref()`, the 404 page's buttons, and breadcrumbs on Insights article pages have all shipped with hardcoded English-only links at least once. When adding or touching any internal link, check it's prefix-aware.

**Astro's built-in `/404` special-casing doesn't extend to `/de/404`.** Astro builds `src/pages/404.astro` to `dist/404.html` (a file, for static-host error page conventions) but `src/pages/de/404.astro` builds to `dist/de/404/index.html` (a directory) — Netlify's automatic "nearest 404.html" behavior won't find it without an explicit `netlify.toml` redirect rule. Also, Astro's sitemap auto-exclusion for `/404` doesn't extend to `/de/404` either — both need explicit handling, and this has been missed and re-broken at least once.

**Insights article author data.** The CSV/database only has opaque author UUIDs, no names. **Never guess an author name from a UUID or from memory of a title-to-author mapping** — always verify against the actual English source page for that specific article. Guessed author attributions have been wrong in multiple past batches (confirmed mismatches across ~6 articles in one batch alone).

**Netlify Forms dashboard shows mixed-language field labels for the `registration` form — this is cosmetic, not a data bug.** `RegisterPageContent.astro` is shared by both `/training/register/[session].astro` and `/de/training/register/[session].astro`, and every field's `name`/`id` attribute is a fixed English literal (`seats`, `address`, `postcode`, `country`, `company`, `vat-id`, etc.) — confirmed unchanged since German registration support was added. What *does* vary by locale is each field's `<label for="...">{t(...)}</label>` text. Because both locale pages render the same `name="registration"` form, Netlify's form-field detector merges the field list site-wide and displays whichever page's `<label>` text it picked up as the "friendly" field name in the dashboard — which is why fields like Seats/Address/Postcode/Country/Company/VAT-ID can show up in German even for an English-page submission. Fields with no `<label>` at all (hidden inputs like `course`/`session-date`, and the `attendee-name-N`/`attendee-email-N` inputs which only have `aria-label`/`placeholder`) fall back to an auto-humanized version of the raw `name` attribute and always stay English. **The actual submitted values and `name` keys are unaffected** — don't "fix" this by hunting for German text in `name`/`id` attributes, there isn't any. The only real fix, if the mixed-language dashboard display is worth addressing, is giving the German page's form a distinct `form-name` (e.g. `registration-de`) — a deliberate scope decision touching `submission-created.js`'s form-name branching, not a bug fix, and not done as of this note.

**Em dashes are prohibited house-wide**, per house style (see below) — check for these in visible content on every change, including article titles, generated copy, and code comments in files that also contain rendered content (script blocks are fine, rendered text is not).

**The `lg` breakpoint is 960px, not Tailwind's 1024px default** (`--breakpoint-lg` in `src/styles/global.css`). Chrome's "desktop site" mode on a phone reports a viewport of about 980px, and with the default every `lg:`-gated layout (header nav vs. Menu button, schedule table vs. cards, multi-column grids) still rendered its tablet version there, which Russ noticed on his own phone. Keep `lg:` as the "real desktop" switch and `md:` (768px) for two-column layouts that also work on a tablet in portrait, like the profile and article page rails. Don't put "find out more" links beside course names in a rail below `lg`; at 768px that squeezes the name to one word per line.

**Redirect targets must be verified against the actual built directory, never guessed from a title.** Several existing articles have a custom `urlSlug` field preserving legacy punctuation (colons, apostrophes, periods, question marks) that differs from what a "clean" slug derived from the title would produce. When redirecting to an existing article, always look up its actual live URL in the built output before using it as a redirect target — a guessed slug will silently 404. This has recurred at least 3 times across the Insights rewrite/cleanup work.

## German translation house style

- **No direct address.** Never use "Sie" or "Du" to address the reader. Use impersonal/collective/passive constructions instead ("Wir unterstützen..." / "Es lohnt sich, ..." / passive voice), consistent with how the whole site is written.
- **Gender-inclusive language** uses the colon form (Trainer:innen, Teilnehmer:innen, Praktiker:innen).
- **English loanwords kept as-is**: Training, Leadership, Facilitation, Coaching, Scrum Master, Product Owner, Sprint, Backlog, and all course/certification codes (FL2D, CSM, CSPO, etc.) — these are standard usage in German-language agile/business contexts, do not translate them.
- **Category/content-type labels** (Change Management, Leadership, Coaching, Flight Levels, Kanban, Blog, Webinar, Agile, Scrum) stay as English loanwords too, **except**: "Product Development" → "Produktentwicklung" and "AI" → "KI".
- **No em dashes** anywhere in rendered content (see gotcha above) — use commas or split into two sentences.
- **German number formatting**: "€1.890" not "€1,890" (period as thousands separator, currency symbol first — matches the rest of the site's `germanizePrice()` convention, NOT the `de-DE` Intl default which puts € after the number).
- **metaTitle convention**: kept identical to the page's own title (English), not prefixed with anything like "Webinar Recording:" — this was a deliberate choice, not an oversight, don't "fix" it to add a prefix.

## Content/routing conventions

- **Trainer/coach display order is a deliberate ranking, driven by `coach-profiles`' `displayOrder` field (lower = earlier; default 10 for anyone with no specific ranking).** Current explicit ranking: Russell Hill (1, the only Fellow actually based in Germany), Konrad Pogorzala (2, Berlin-based), Javier Perez Fernandez (3, built his career in Berlin though his profile now shows Madrid — kept per Russ's explicit ranking, not a data error), Bent Myllerup (4), Giuseppe De Simone (5); everyone else shares the default (10) and falls back to alphabetical. **Every trainer listing site-wide must respect this** — `getTrainersForSessions()` (`src/lib/trainers.ts`) sorts by it for course/category/self-paced/register pages and schedule rows, and the About page's team grid sorts by it directly. When adding a new coach profile or changing this ranking, this is the one field to touch — don't hardcode name-based ordering anywhere. **The homepage's team teaser is the one exception** — see the next entry.
- **Homepage team teaser rotates daily, not by `displayOrder`.** `getHomepageTeam()` (`src/lib/team.ts`) always leads with Russell Hill, Konrad Pogorzala, and Javier Perez Fernandez (hardcoded by id — the 3 Germany-based, even if partly, Fellows), then fills 5 more slots from everyone else with `hasFullProfile: true`, rotating daily (2 from the `isFemale: true` pool, 3 from everyone else), guaranteeing at least 2 women every day rather than on average. `isFemale` is a plain boolean on `coach-profiles`, set explicitly per person (Camilla Bergkvist, Heidi Reidel Sørensen, Joanne Perold, Julia Västrik today) — deliberately not inferred from bio pronouns, so it's a correctable fact instead of a guess. As with every other date-driven thing on this static site, "daily" means once per nightly rebuild, not literally every page load — a genuinely-different-every-refresh version would need client-side JS, which was deliberately not used here (see `src/lib/team.ts`'s own comments).
- **`/de/insights` hub now exists** (shipped from `betterchange-de-translation-draft-insights-template.md`, using its translations for the shared template strings — heading, intro, category filters, newsletter, etc.). It shows all ~200 articles, same as the English hub: the ~81 with a German translation link to `/de/insights/[slug]`, the rest link out to their English page at `/insights/[slug]` instead of hiding them or 404ing — the same graceful-fallback pattern as the language switcher on untranslated pages, implemented via `localizedArticle()` (`src/lib/i18n.ts`) plus `InsightsArticleCard`'s existing per-article-own-locale href/date logic. Breadcrumbs, header nav, and footer on German pages now correctly link to `/de/insights` (previously they deliberately pointed at the English hub since this route didn't exist yet — if you find code still doing that, it's stale, not intentional). The two hub pages share one component, `InsightsHubPageContent.astro`, same split pattern as `RegisterPageContent.astro`.
- **Category filter tags on the German hub are normalized in code, not trusted from data**: `primaryCategory` on a German article's own frontmatter isn't reliably already using the "Produktentwicklung"/"KI" house-style labels (at least one published article still has `primaryCategory: AI` untranslated), and a fallback card showing an English article's frontmatter is always in English regardless. `InsightsHubPageContent.astro`'s `displayCategory()` maps both to the correct German label for the filter buttons/grouping regardless of what the source data says — don't remove it as "redundant" without checking the actual frontmatter across all DE articles first.
- **German course pages use short certification-code slugs**, not a translated version of the English long-form slug — e.g. `/de/training/scrum/csm/`, not a German equivalent of `/training/scrum/certified-scrum-master-(csm)`. This is intentional, documented, and shared with how Insights article locale routing works.
- **Article title translation**: article titles are kept in English on the German pages (not translated), consistent with how course names are handled.
- **"Related training" block on Insights article pages is computed, not authored.** `src/lib/relatedTraining.ts` matches each article to 1-3 courses at build time: a keyword-scoring tier (role terms, course codes, sprint/backlog/retrospective/kanban/flight-levels/SAFe/AI counts, with role-dominance rules so a Product Owner article never gets CSM filler) and, when nothing clears the threshold, a fallback tier keyed off the article's primary category and topical signals. German article pages reuse the *English* original's mapping and resolve to the `de/` course entries, so a course must exist in both locales to show on both. Articles where a course pitch would read badly are listed by slug in `NEVER_MATCH` at the top of that file (currently the hedgehogs article and the certification-circus mishap); that's the only place to opt an article out, don't add per-article frontmatter for it. The matching was calibrated on a reviewed sample; when changing thresholds, re-check those sample articles rather than only the one you're fixing. **The Flight Levels Introduction (FLIN) never appears as the only Flight Levels pick** (per Russ: it's the course people take *before* a real FL course), so the matcher adds FL3D (strategy articles) or FL2D right after it, which is the one case the list can grow to four. **The card's connective sentence** ("Want to build a product vision? These courses...") comes from `insights.trainingIntro.<signal>` in `src/i18n/ui.ts`, keyed off the matcher's `signal`; an article's own `relatedTrainingIntro` frontmatter overrides it, per locale (the German one must follow the no-direct-address rule). The 14 reviewed sample articles have hand-written ones; everything else uses the template until someone writes a better one.

## Safety / testing

- **LEXWARE_TEST_MODE** must be confirmed enabled before any end-to-end registration/payment flow is tested. When true, invoices are created as drafts prefixed "TEST —" and never finalized. Never test the registration flow without first confirming this is on.
- This is a **static Astro build** — Lexware integration lives in Netlify Functions, which are NOT reachable from a local dev/preview server or from a sandboxed session with blocked network egress. Functional/payment-flow testing can only be done by a human directly on the live site (or a deploy preview with function access), not by an AI session running in an isolated sandbox.

## Pre-merge checklist (used successfully twice, reuse for future merges)

Before merging any branch back to `main`, run and report pass/fail on:
1. Full `[DE]`-placeholder scan across the whole site
2. Hreflang and canonical tags on all new/changed pages
3. Language switcher behaviour on all affected page types
4. Locale-aware links, full audit (see gotcha above)
5. Sitemap inclusion for all new URLs, both locales
6. Build health (clean rebuild + `astro check`)
7. Leaked/duplicated content scan (dev notes, placeholder text, WP-import artifacts)
8. Shared-component consistency (mega-menu, footer, closing CTAs) across all new page types
